# Диагностика dub_22 и dub_23

Готовый Python-модуль для парного сравнения банковских CatBoost-моделей и поиска источников ухудшения Gini. Рабочие модели и банковские данные в проект не включены. `demo_data` содержит только сгенерированный пример.

## Три уровня анализа

1. **Подмодели:** качество исходных скоров early/long/soc_dem, различия версий, CI и переранжирование; регрессия прироста Gini итогового dub_23 относительно dub_22 через качество этих скоров. Подмодели не калиброваны, их PD не требуются.
2. **Итоговые скоры:** парное сравнение `score_dub_22`/`score_dub_23` и отдельно `pd_dub_22`/`pd_dub_23`, доверительные интервалы, количество переранжированных дефолтов и точное количество изменившихся bad–good пар.
3. **Признаки:** SHAP, чувствительность ранжирования к отдельному признаку/группе, замены компонентных входов, сплиты и потоки по веткам/листьям.

Новый блок конфигурации — `analysis_levels` в `config.example.json`; он работает и с `--scores-only`, без `.cbm`. Для признаков и деревьев `.cbm` по-прежнему нужны. Старые конфиги без этого блока сохраняют прежний режим, дополненный точной статистикой пар.

## Запуск на ваших данных

Требуется Python 3.10+.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp config.example.json config.json
# В config.json указать пути к данным, .cbm и папке результата
python diagnose.py --config config.json
```

Если пока доступны только сохранённые PD:

```bash
python diagnose.py --config config.json --scores-only
```

Из Python или Jupyter:

```python
import json
from diagnose import run

with open("config.json", encoding="utf-8") as file:
    cfg = json.load(file)
tables = run(cfg)
tables["metrics"]
tables["reranked_defaults"].query("status == 'worse'")
tables["component_swaps"].query("scope == 'recent'")
```

Вход: один CSV/Parquet, одна строка на `App_id`, исходные признаки и скоры обеих моделей на одной заявке.

| Поле | Значение |
|---|---|
| `App_id` | Уникальная заявка; дубли останавливают запуск |
| `issue_dt` | Дата выдачи; месячные срезы |
| `flag_4m_30p_gross` | Основной таргет 30@4: 0/1; неизвестный исход — NA |
| `flag_6m_30p_gross` | Дополнительная проверка 30@6 на своей вызревшей выборке |
| `pd_dub_22`, `pd_dub_23` | Больший PD означает больший риск |
| `score_dub_22`, `score_dub_23` | Чистые скоры итоговых моделей до внешней калибровки |
| `early_model_dub_22`, `long_model_dub_22`, `soc_dem_dub_22` | Компонентные скоры для dub_22 |
| `early_model_dub_23`, `long_model_dub_23` | Компонентные скоры для dub_23 |
| `fps*` | FPS-признаки |
| Остальные признаки | В точности production preprocessing обеих моделей |

Компоненты — отдельные бустинги, поданные в итоговый бустинг как скоры. Здесь разбираются **деревья итоговых dub_22/dub_23**. Чтобы исследовать деревья самих early/long/soc_dem, дополнительно нужны их `.cbm`, исходные признаки и соответствующие подтаргеты.

В `feature_map` слева — **имя признака внутри сохранённой модели**, справа — колонка данных. Например, native `early_model` сопоставляется с `early_model_dub_22`. Если модель уже обучена с суффиксами, лишние соответствия можно удалить: неуказанные имена берутся напрямую. Для группировки ожидаются префиксы `early_model`, `long_model`, `soc_dem`, `fps`; прочие признаки попадают в `other`.

При включённом `analysis_levels` модель сверяется с **чистым скором** из `raw_score_col`, а не с внешне калиброванным PD: калибровка по сегментам может законно изменить общий порядок. При необходимости поле `models.<model>.verification_score_col` задаёт колонку сверки явно. Расхождение останавливает интерпретацию: анализ другого артефакта объяснял бы другой скор. Порог `min_score_spearman` по умолчанию 0.99999. Калиброванный PD должен быть предоставлен: `predict_proba` из `.cbm` не подменяет внешний calibrator. Только в прежнем режиме, без `analysis_levels`, отсутствующий PD рассчитывается из модели, а имеющийся используется для сверки.

В примере **подтверждены** названия итоговых чистых скоров `score_dub_22`, `score_dub_23` и PD `pd_dub_22`, `pd_dub_23`. **Калиброваны только итоговые модели.** Подмодели заданы исходными скорами `early_model_dub_22`, `long_model_dub_22`, `soc_dem_dub_22` и соответствующими колонками версии 23. В `analysis_levels.submodels` достаточно `raw_score_col` и `raw_higher_is_risk`; калиброванные PD подмоделей не нужны и не генерируются. Даже если старый конфиг содержит у подмодели `pd_col`, это поле не используется. Направление каждого raw задаётся `raw_higher_is_risk` (по умолчанию `true`, требуется проверить для подмоделей).

## 1. Сколько дефолтов переранжировали лучше

Для каждого дефолта **внутри своего месяца** считается:

```text
q_m(i) = [число good со скором < score_m(i)
          + 0.5 × число good с равным скором] / число good

quality_delta(i) = q_23(i) - q_22(i)

quality_delta > 0: дефолт стал лучше отделяться от good
quality_delta < 0: дефолт стал хуже отделяться от good

Gini_m = 2 × mean(q_m(i) по дефолтам) - 1
ΔGini = sum(2 × quality_delta(i) / число дефолтов)
```

Это точное разложение Gini без перебора всех пар bad–good, включая равные скоры. Простое движение PD или общего процентиля не равно улучшению Gini: положение относительно других дефолтов на AUC не влияет.

- `metrics.csv`: `defaults_better`, `defaults_worse`, `defaults_unchanged`, `delta_gini_23_minus_22` и CI. Для окна `recent` все пары считаются внутри объединённого окна; помесячные счётчики могут давать другую сумму.
- `reranked_defaults.csv`: конкретные `App_id`, оба q, `quality_delta`, `status`, вклад в месячный ΔGini. `net_pair_units` — **чистый баланс** пар с учётом половины за ties; это не количество всех исправленных пар отдельно от испорченных.
- `top_risk.csv`: при одинаковой доле отклонения `reject_rates` сколько дефолтов стали ловить дополнительно и сколько потеряли; также recall и новые ошибочные отклонения good.
- `top_risk_migrations.csv`: конкретные заявки, пересёкшие границу решения, по месяцам.

Теперь точные переходы пар считаются отдельно от чистого баланса:

| Поле | Значение |
|---|---|
| `pairs_bad_good_total` | Общее число bad × good пар |
| `pairs_wrong_to_correct` | Строго неверно упорядоченные пары стали строго верными |
| `pairs_correct_to_wrong` | Строго верные стали строго неверными |
| `pairs_improved` | Все улучшенные пары, включая wrong→tie и tie→correct |
| `pairs_worsened` | Все ухудшенные пары, включая correct→tie и tie→wrong |
| `pair_gain_units`, `pair_loss_units` | Полный переход даёт 1, переход через tie — 0.5 |

Все 9 сочетаний wrong/tie/correct доступны в `levels_pair_transitions.csv`, а счётчики — также в `metrics.csv`, `reranked_defaults.csv`, `levels_metrics.csv` и `levels_defaults.csv`. Исправленные и испорченные пары могут одновременно присутствовать у одного дефолта даже при нулевом чистом изменении его качества. Число дефолтов `better/worse` определяется **чистым** изменением положения относительно good. Проверяется тождество `ΔGini = 2 × (pair_gain_units − pair_loss_units) / (n_bad × n_good)`. Подсчёт точный, без семплирования пар и без матрицы bad × good; сложность O(N log N). CI относятся к Gini и вероятностным метрикам; счётчики пар/дефолтов — точные значения на данной выборке, отдельные CI для них не рассчитываются.

## Сравнение raw score и калиброванного PD

Для итоговых моделей используются одинаковые заявки с четырьмя конечными значениями: raw_22, raw_23, PD_22, PD_23. Пропуски отражаются в `levels_cohort_audit.csv`. Для каждой подмодели требуется только пара исходных скоров версий 22/23; у soc_dem доступна одна версия. Объём каждой выборки явно указан. Регрессия использует общую полную выборку четырёх итоговых выходов и исходных скоров подмоделей.

`calibration_gap_decomposition.csv` вычисляет по месяцам, reference, recent и всей выборке:

```text
raw_gini_gap = Gini(score_dub_23) − Gini(score_dub_22)
pd_gini_gap  = Gini(pd_dub_23)    − Gini(pd_dub_22)

gap_change_due_to_calibration = pd_gini_gap − raw_gini_gap
                             = (Gini(PD_23) − Gini(raw_23))
                               − (Gini(PD_22) − Gini(raw_22))
```

Отрицательное значение последней величины означает, что переход к PD ухудшил относительное ранжирование версии 23 по сравнению с её raw-разрывом. Это точное сравнение предоставленных скоров на одних строках с paired bootstrap CI; оно предполагает корректную связь колонок raw и PD с одной моделью. Для pooled окон разные калибровки по месяцам могут менять межмесячные пары даже при сохранении Gini каждого месяца.

В `levels_metrics.csv` фильтруйте `entity=final`, `representation=raw/pd`. Таблица `levels_top_risk.csv` дополняет это сравнением при одинаковой доле отклонения до и после калибровки. `levels_overview.png` показывает обе динамики. `submodel_quality.csv` содержит `gini_raw` каждого входного бустинга и CI, включая единственную soc_dem_22; `levels_metrics.csv` сравнивает версии подмоделей только на их исходных скорах (`representation=raw`). Все калибровочные отчёты относятся только к `entity=final`.

В `calibration_metrics.csv`:

- `delta_gini`: Gini(PD) − Gini(raw) для конкретной модели; CI и полная статистика пар/дефолтов.
- `single_strictly_increasing_mapping`: проверка единой строго возрастающей зависимости PD от ориентированного raw. Она сохраняет ранжирование. Округление, клиппинг и isotonic-плато могут создавать ties; разные calibrator по сегментам/времени — перестановки между группами. `raw_equal_groups_with_different_pd` и `raw_groups_with_order_violation` проверяют нарушение единой зависимости на всех заявках, а не только на bad–good парах.
- Brier, LogLoss, средний PD, observed/expected ratio, ECE по общим фиксированным бинам из `pd_bins`, диагностические calibration intercept и slope. Для идеального соответствия вероятностей таргету ориентиры: intercept=0, slope=1. GLM fit на оценочной выборке служит измерением, не заменяет calibrator и не используется для пересчёта PD.
- `calibration_curves.csv`: средний PD и фактическая частота в каждом бине. Wilson CI предполагает независимость строк; при `cluster_col` эти локальные Wilson-интервалы не выдаются, тогда как bootstrap агрегированных метрик и GLM covariance учитывают кластер.

**Таргет итогового PD:** у каждой итоговой модели задайте `pd_target` — имя таргета, под который калибровался её PD. Если он доступен, Brier/LogLoss/reliability/GLM рассчитываются на его наблюдаемых исходах (`probability_target`, `n_probability_evaluation`), а Gini для сравнения версий — на основном `30@4` (`ranking_target`). Если целевой таргет PD неизвестен (`null`) или его нет в данных, метрики вероятностей относительно `30@4` выводятся как диагностические и отмечаются предупреждением. Они не доказывают плохую калибровку модели, предназначенной для другого таргета. Подмодели обучались на разных подтаргетах, но не калиброваны: для них здесь оценивается только ранжирование по основному `30@4`.

Для сравнения Brier/LogLoss **до и после** калибровки нужна некалиброванная вероятность, а не произвольный raw score. Настройте одно из:

```json
{"uncalibrated_pd_col": "pd_uncalibrated_dub_22", "raw_kind": "score"}
{"raw_kind": "probability"}
{"raw_kind": "margin"}
```

Первый вариант использует сохранённую вероятность до calibrator. Во втором raw уже является вероятностью (направление учитывается). Третий допустим для настоящего logit/RawFormulaVal бинарного Logloss-CatBoost и применяет sigmoid; для произвольного балла он неверен. При `raw_kind=score` без `uncalibrated_pd_col` сравнение рангов работает полностью, но исходные Brier/LogLoss не выдумываются. Отрицательные `brier_change_pd_minus_uncalibrated` / `logloss_change_pd_minus_uncalibrated` означают улучшение вероятностной ошибки. Их CI используют обычный парный case bootstrap, а не стратификацию по y, чтобы учитывать неопределённость частоты дефолта. Gini CI по-прежнему стратифицированы по y или используют кластерный bootstrap.

Если calibrator зависит от канала, продукта или версии, задайте `calibration_group_cols` в спецификации модели. Дополнительно появятся проверки score→PD внутри этих групп; для них CI не считаются, чтобы не смешивать их с основными парными CI. Монотонность по группам не гарантирует сохранение глобального Gini.

## Регрессия прироста Gini через подмодели

Строятся две описательные регрессии с **одинаковыми предикторами — качествами некалиброванных скоров подмоделей**. Меняется только response: разрыв итогового Gini до калибровки (`representation=raw`) или после неё (`representation=pd`):

```text
Gini(final_23_representation, t) − Gini(final_22_representation, t)
    = β0
    + β1 × [Gini(early_23, t) − Gini(early_22, t)]
    + β2 × [Gini(long_23, t) − Gini(long_22, t)]
    + β3 × Gini(soc_dem_22, t)
    + ε_t
```

Все Gini для этой задачи измеряются на основном таргете `30@4`. В правой части всегда используются только исходные скоры подмоделей; в panel это отмечено `predictor_representation=raw`. Набор `regression.predictors` изменяемый: можно использовать разницы качеств или отдельные `gini__<component>__<version>`. Качество soc_dem_22 включено как имеющаяся компонента версии 22; Gini отсутствующей soc_dem_23 не подставляется нулём.

По умолчанию единица наблюдения — **неперекрывающийся месяц**, допустимы также `frequency=W` или `Q`. Bootstrap-реплики не превращаются в дополнительные месяцы; автоматически дробить пять месяцев для получения «значимости» код не будет. Если использовать недели, сначала убедитесь, что в каждой хватает дефолтов и отсутствие зависимости правдоподобно с выбранными HAC-lags.

По умолчанию `split_measurement=true`: внутри каждого периода target-independent hash по `cluster_col` (или `App_id`) делит клиентов на две непересекающиеся половины. Качество подмоделей измеряется на одной, итоговый разрыв — на другой. Один клиент остаётся в одной половине по всем периодам. Это уменьшает общую ошибку измерения из-за тех же самых размеченных заявок. Оно не устраняет все ошибки измерения, корреляции и смешение по времени. При отключении — обычная описательная регрессия общих срезов.

Проверяются минимальные bad/good **в каждой половине**, достаточное число периодов (по умолчанию минимум 12, и не менее числа предикторов + 8), отсутствие констант, коллинеарности и пропущенных временных периодов. Интервалы коэффициентов — HAC/Newey–West с `hac_lags`; исходные и стандартизованные коэффициенты сохранены. Параметры HAC не исправляют неверную спецификацию или малое число периодов. При достаточной истории дополнительно оценивается прогноз на последних 25% периодов из регрессии, обученной только на более ранних, с baseline-прогнозом среднего.

- `submodel_regression_panel.csv` — измеренные временные точки, объёмы половин, response и качества подмоделей.
- `submodel_regression_coefficients.csv` — коэффициенты, CI и p-value; положительный β1 означает связь улучшения early_23 с улучшением final_23 относительно final_22 при прочих включённых регрессорах.
- `submodel_regression_diagnostics.csv` — status, число периодов, R², condition number, chronological holdout RMSE.
- `submodel_regression_fitted.csv` — фактический разрыв, in-sample fitted и отдельные прогнозы chronological holdout.

Если доступны только декабрь–апрель, **пяти месяцев недостаточно** для указанной регрессии: будут panel и `insufficient_periods`, а таблица коэффициентов останется пустой. Для регрессии добавьте более длинную **вневыборочную** историю: исходные `reference_periods` и `recent_periods` задают окна сравнения, но regression panel использует все вызревшие строки входного файла. Не добавляйте train-строки production-модели ради увеличения числа точек. Полученные коэффициенты показывают связь качества, не причинный вклад подмодели.

При ties на границе top-K используется единый детерминированный порядок по `App_id`; отдельно выводится ожидаемое число дефолтов при случайном выборе среди ties. Гипотетическое отклонение означает offline-расчёт по уже наблюдаемым клиентам, а не фактическое изменение банковского решения.

## 2. Какая компонента связана с падением

Используйте несколько согласующихся проверок:

1. `component_gini.csv`: собственный Gini early/long/soc_dem по времени. Проверяет, ухудшился ли входной скор сам по себе. Направление задаётся отдельно в `components`.
2. `score_correlations.csv`: изменились ли ранги компонент между версиями; одинаковые по названию компоненты могут иметь разные значения.
3. `component_swaps.csv`: итоговая модель остаётся фиксированной, но один входной компонентный скор заменяется скором другой версии, затем early/long заменяются совместно. Положительный `improvement` означает, что подстановка улучшила Gini. Проверка имеет смысл при совместимых шкалах и preprocessing; гибридные входы могут не соответствовать обучающему распределению.
4. `shap_features.csv`, `shap_groups.csv`: куда сместились вклады в **raw logit**, рассчитанные через Independent Tree SHAP с одними reference-заявками для двух моделей. Абсолютный SHAP не является вкладом в Gini.
5. `gini_group_allocation.csv`: точное описательное разложение разрыва Gini на **диагностической подвыборке** по early, long, soc_dem, fps, other. Для 32 комбинаций групп строятся гибриды `raw_22 + сумма(SHAP_23_group − SHAP_22_group)` и по ним вычисляется Shapley-разложение изменения Gini. Сумма групп равна ΔGini на той же подвыборке; отрицательные группы тянут разрыв вниз. Разница констант SHAP не влияет на ранжирование. Распределение взаимодействий зависит от этой схемы гибридов и raw-шкал моделей.
6. `shap_group_removal.csv`: меняется ли Gini при вычитании SHAP группы. Это другая диагностическая аппроксимация, не модель, переобученная без признаков.

На уровне отдельного признака `shap_features.csv` дополнен `gini_full`, `gini_without_shap_feature`, `improvement_without_shap_feature`. Положительное последнее значение означает, что вычитание его raw SHAP-вклада улучшило ранжирование на диагностической подвыборке. Это чувствительность готовой модели, не эффект переобучения без признака. Поля `explained_output=CatBoost RawFormulaVal`, `external_calibrator_included=false` подчёркивают: SHAP и деревья объясняют итоговый бустинг до калибровки, а его внешняя калибровка анализируется отдельными таблицами. Исходные скоры подмоделей подаются в него без отдельной калибровки и используются как обычные входные признаки.

Если у early_23 падает собственный Gini, замена на early_22 улучшает итоговый dub_23, а группа early даёт отрицательное изменение вклада в разрыв, это согласованная зацепка для проверки early. Одного большого SHAP/FI для такого вывода недостаточно. Причинность из этих проверок не следует.

## 3. Где именно изменяются сплиты и маршруты

В готовом CatBoost сплиты фиксированы. На новых выдачах меняются маршруты клиентов и качество разделения. Добавление FPS при **обучении** может поменять всю последовательность деревьев; номер дерева dub_22 не соответствует тому же номеру dub_23.

- `tree_blocks.csv`: накопительный Gini по `tree_step` деревьев, прирост на блоке, изменение прироста recent относительно reference, улучшение Gini при удалении блока из полного raw score. Положительный `improvement_without_block_recent` выделяет блоки, которые ухудшают текущее ранжирование в составе готовой модели. Это не переобучение без блока.
- `tree_splits.csv`: **все** сплиты — номер дерева, глубина, признак/комбинация CTR, порог, исходное JSON-условие. `tree_start` и `tree` нумеруются с 0, `tree_end_exclusive` — исключающая правая граница.
- `split_profile.csv`: частота групп на разных глубинах.
- `tree_branches.csv`: для выбранных деревьев — `tree`, `depth`, `node_prefix`, `branch`, объёмы, bad rate, доля ветви внутри узла и их изменения. `reliable_size` отмечает наличие достаточного числа bad и good в обоих окнах.
- `tree_leaves.csv`: распределения и bad rate по листьям, значение листа в raw score до общей model scale/bias.

Локальный анализ выбирает до `max_local_trees` деревьев из блоков, удаление которых сильнее помогает на recent. Для полного анализа увеличьте лимит и поставьте `tree_step=1`; отчёты и время расчёта вырастут. Если блоков с положительным эффектом удаления нет, будут показаны наиболее неблагоприятные из имеющихся.

Роутинг берётся из `calc_leaf_indexes`, включая categorical/CTR и пропуски числовых признаков. Сложные CTR не подменяются наивным сравнением исходного признака с порогом. Для симметричного дерева бит `depth` индекса листа задаёт исход сплита, `node_prefix` — предыдущие биты пути; ветка 1 означает истинный бинаризованный предикат (у float — `x > border`, у one-hot — равенство хеша). Ветка 1 сама по себе не означает больший риск. Для асимметричных деревьев остаются блочные метрики, а локальная раскладка пропускается с записью ограничения. Неизвестная структура CTR также явно отмечается.

Пример поиска мест для разбора:

```python
import pandas as pd

blocks = pd.read_csv("reports/dub_comparison/tree_blocks.csv")
blocks.query("model == 'dub_23'").sort_values(
    "improvement_without_block_recent", ascending=False
).head(10)

branches = pd.read_csv("reports/dub_comparison/tree_branches.csv")
branches.query("model == 'dub_23' and reliable_size").sort_values(
    "branch_share_shift", key=abs, ascending=False
).head(20)

allocation = pd.read_csv("reports/dub_comparison/gini_group_allocation.csv")
allocation.query("scope in ['reference', 'recent']").pivot(
    index="group", columns="scope", values="gini_delta_allocation"
)
```

Малые узлы, найденные после просмотра тысяч сплитов, не являются статистическим доказательством. Подтвердите зацепку на следующем OOT-периоде.

## 4. Дополнительная диагностика

- `data_quality.csv`: сколько заявок было, сколько укладываются в cutoff, имеют таргет и оба скора. NA никогда не превращается в good.
- `metrics.csv`: paired bootstrap CI разницы Gini на одних заявках; по умолчанию выборка стратифицирована по таргету. При повторных клиентах задайте `cluster_col` с ID клиента — все его заявки ресемплируются вместе. `App_id` остаётся уникальным ID заявки.
- `window_gap_change.csv`: изменение Gini каждой модели и изменение разрыва recent−reference с joint bootstrap CI. Отрицательное изменение разрыва означает, что dub_23 относительно dub_22 ухудшился сильнее. Кластерный bootstrap сохраняет зависимость клиента между окнами.
- `drift.csv`: PSI по бинам reference, отдельный учёт NA, изменение доли пропусков, числа уникальных значений. PSI — индикатор сдвига, не тест причины падения. Распределение считается на парной вызревшей выборке.
- `segments.csv`: Gini по заданным в `segments` категориям (канал, продукт, регион и т.д.). Числовые признаки заранее разбейте на осмысленные интервалы.
- `secondary_flag_6m_30p_gross.csv`: проверка дополнительного таргета. Если он ещё не вызрел на recent, метрики отсутствуют/NA; недостающие месяцы перечисляются в summary.
- `model_features.csv`, `model_parameters.json`: фактические признаки, mapping, гиперпараметры. Проверьте различия objective, train-периодов, seed, iterations, depth, regularization, sampling и версии компонент.
- `manifest.json`: версии библиотек, контрольные суммы `.cbm` и ограничения запуска.
- `overview.png`, `summary.md`: обзор результата.

**Ваши настройки:** основной таргет вызрел по апрель 2026 включительно; `max_issue_date=2026-04-30`. Последние точки заданы как март–апрель 2026, reference — декабрь 2025–февраль 2026. Это настраиваемое предположение: замените окна, если ухудшение началось раньше/позже. При `null` окна выводятся как последние два доступных месяца и до трёх предыдущих. Для 30@6 валидность каждого non-NA остаётся обязанностью источника данных.

Все Gini в CSV представлены на шкале `[-1, 1]`: `0.01` = один пункт Gini. Метрики без весов. Bootstrap учитывает неопределённость выборки при фиксированных моделях, но не вариативность обучения; сравнение окон смешивает эффекты времени и состава выдач. Pooled Gini включает межмесячные пары, поэтому всегда смотрите помесячный результат. На выданных кредитах нельзя оценить качество на всём потоке заявок, если неизвестны исходы отказанных.

Полные ранжирования и bootstrap считаются на всей парной выборке. SHAP/гибриды/деревья — на воспроизводимой равномерной подвыборке до `diagnostic_sample_per_window` объектов **из каждого окна**. Её метрики записываются в `diagnostic_sample_metrics.csv`: сначала сравните их с полной выборкой, при необходимости увеличьте лимит. Не используйте поисковые выводы этой подвыборки для настройки модели без нового независимого OOT.

## Проверка FPS отдельно от удаления soc_dem

В описанных моделях одновременно меняются как минимум два блока: добавлены FPS и убран soc_dem. Если значения early/long между версиями различаются, появляется ещё один фактор. Отключение FPS в готовой модели не восстанавливает модель без FPS.

`ablation.py` переобучает четыре модели на одинаковых train/validation/OOT, с одинаковыми остальными входами и фиксированным числом деревьев:

| Вариант | Общая база, включая фиксированные early/long | soc_dem | FPS |
|---|---|---|---|
| base | да | нет | нет |
| soc_dem | да | да | нет |
| fps | да | нет | да |
| soc_dem_fps | да | да | да |

```bash
cp ablation.example.json ablation.json
# Указать настоящие признаки общей базы и train/validation/OOT
python ablation.py --config ablation.json
```

`base_features` должен содержать **полный** общий набор, но одинаковые early/long из одной фиксированной версии для всех четырёх вариантов. Значения `common_feature_1/2` в примере — placeholders. Компонентные скоры на train должны быть OOF/out-of-time; в validation/OOT компоненты должны быть обучены только на более ранних данных. Код не может проверить происхождение подготовленных скоров автоматически.

Обучение использует фиксированные iterations, без early stopping, чтобы число деревьев было одинаковым. Validation передаётся только для оценки; OOT вообще не участвует в fit. Число деревьев и параметры заранее выбираются на отдельных train/validation. Проверяется временной порядок и отсутствие общих `App_id` между выборками. Все четыре варианта оцениваются на одинаковых строках; NA числовых признаков обрабатываются CatBoost, NA категориальных требуют production preprocessing.

`ablation_effects.csv` содержит эффект добавления FPS с/без soc_dem, добавления soc_dem с/без FPS, взаимодействие и разницу структуры «FPS без soc_dem» против «soc_dem без FPS». Отрицательный эффект FPS на recent при одинаковой базе поддерживает гипотезу вреда FPS для текущего OOT. Сравните эффект по нескольким seed. Это условный результат конкретного обучения, а не восстановление истории production-моделей; отдельно исследуйте смену самих компонент и preprocessing. CI даются для парных сравнений фиксированных переобученных моделей; вариативность seed показывается отдельными строками.

## Синтетический пример и проверки

```bash
python make_demo.py
python diagnose.py --config demo_data/config.json
python ablation.py --config demo_data/ablation_config.json
python -m pytest -q
```

Пример намеренно меняет связь FPS с таргетом на последних месяцах и немного портит early_23. Он проверяет механику диагностики и не характеризует реальные модели банка. Сгенерированные компонентные скоры — искусственные входы, не обученные submodels.

Тесты проверяют точное разложение Gini с ties, фильтрацию незрелых таргетов и дублей, парный/кластерный bootstrap, квоты отклонения, аддитивность групп, drift констант, numeric/one-hot/CTR-сплиты, порядок битов листа и защиту от временной утечки.

Расширенные тесты также сверяют все 9 переходов пар с полным перебором, взвешенный Gini с ROC AUC, инвариантность монотонной калибровки, влияние округления и сегментных calibrator, одинаковые raw/PD cohorts, собственный таргет PD и его вызревание, split измерений, HAC-регрессию, holdout и отказ от оценивания на пяти точках.
